# Multi-Window Navigation

**Status:** future · **Priority:** high

Runtime control for showing, closing, and navigating between windows. The `WindowManager` singleton already tracks windows; `open()` and `navigate()` are stubs waiting to be wired.

## Why it matters

- Apps that grow windows at runtime (settings, dialogs, tools)
- Navigation between pages inside a window (see [File-Based Windows & Pages](file-routing.md))
- Declarative morph-actions for windows (`morph-open`, `morph-close`, `morph-navigate`) are **already generated by the event emitter** — they just call stubs

## Planned API — via `useWindow`

Navigation and window control go through the `useWindow` hook, not static `App` calls. Inside any component:

```ts
const win = useWindow()              // the window rendering this component
const win = useWindow("settings-win")  // any window, by id given at creation
const win = useWindow("/auth/login")   // or by route id (opens if not running)

win.navigate("/settings", { theme: "dark" })  // swap this window's page
win.close()
win.show() / win.hide()
win.title = "New Title"
win.on('close', () => { ... })
```

New windows are created by opening a route as a window:

```ts
const settings = new Window("/settings", { width: 500, height: 400 })
```

## Underlying runtime (`WindowManager`)

```cpp
void open(const std::string& windowId);        // show a registered window
void close(const std::string& windowId);       // ✅ implemented (delete + erase)
void navigate(const std::string& windowId,
              const std::string& pageId);      // swap the window's page
```

The event emitter (`morph/codegen/event_emitter.py`) already generates these calls for JSX event handlers:

```tsx
<button morph-open="settings">Open Settings</button>
<button morph-close="settings">Close Settings</button>
<button morph-navigate="main:home">Go Home</button>
```

## How it will work

- **`open()`** — windows created from files are registered but can start hidden; `open` triggers show + layout + first paint. Requires `MorphWindow` to support "created but hidden" state (GLFW `glfwShowWindow`/`glfwHideWindow`)
- **`navigate()`** — per-window page mounting. Each window owns one root layout tree; navigating swaps the root content (reusing the node-tree swap machinery that hot reload already uses) and delivers `props` to the new page component
- **`close()`** — exists and works: deletes the window and erases it from the manager

## Open questions

- **Page model** — pages come from the `route.mx` manifest (folder path = route id); does `navigate` need a history stack (back/forward) or is a direct swap enough?
- **Compositor** — each window owns a GL context on the compositor thread; opening a second window means a second context or context sharing
